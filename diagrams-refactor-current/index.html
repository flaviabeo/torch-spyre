Why y + 1 still cannot overlap the collective

The graph is correct now, but the stream still serializes

The refactor puts y + 1 where overlap would happen, between allreduce_run and wait_work. The runtime then removes the overlap in the same two ways as before. First, allreduce_run appends the seven collective ops to stream 1 before fused_add_1.run appends its two, and the stream is in order. Second, the first of those two is an H2D after COMPUTE-queue ops, so STRICT_ORDERING puts a host barrier in front of it that waits for every compute fence:

In this run the cost is small, 0.12 ms, because the ranks arrived close together and no RDMA wait stalled. On 20 Oct the same barrier held y + 1 for 1.06 ms behind a stuck RDMA wait. The structure has not changed: real overlap still needs the collective and the compute on separate streams, or separate hardware queues, so that a slow RDMA wait would hold only the collective.

Rank skew is small in this run

Rank 1 started the WorkSchedule 0.68 ms before rank 0, so its data was already in staging when rank 0 reached its RDMA waits. Rank 1's own waits took 331 and 292 µs instead. On 20 Oct rank 1 was 3 ms behind and rank 0's second wait sat on the device for 1.23 ms. Skew is a property of the driver, not of the refactor, and changes from run to run.

Debug logging inflates host gaps

This run used DTLOG_LEVEL=debug, about 20 lines per CB. The 0.1–0.3 ms between one doorbell and the next is mostly host work and logging, so treat the absolute numbers as upper bounds.

Rank 1 is the mirror image

It writes its contribution to staging +0x100, waits on RDMA masks 16 and 2, and loads its add kernel from …/ops/rank_1/key_wsi_0/…. Its CB tags are now the same as rank 0's.

Seven collective CBs now, not eight

spyre-comms now sends D2H, RDMA wait, H2D of both halves, the sum, a 128 B D2H, a second RDMA wait, and comms_ws_end. On 20 Oct it sent D2H, an H2D/D2H swap, two RDMA waits back to back, H2D, the sum, and null_op. The sum now runs right after the first wait.
